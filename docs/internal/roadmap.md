# Roadmap

Planned features sorted by value/complexity ratio for commercial readiness.

## Active

Sequenced by dependency and priority — items higher up are unblocked
and ship first, items further down build on what came before.

The first five items gate the public release and announcement: they are
what a first-time visitor — or a buyer's technical evaluator — checks
before anything else, and every one of them is currently missing or
broken in the public repo.

| Feature | Complexity | Why |
|---------|:---:|-----|
| Reproducible public benchmark harness | Medium | The README's headline figures (`p99 404 µs @ 1.00M/s`, 66 µs single-event floor) are measured against the separately-distributed Exchange Core, and the README says so: "the benchmark harness and tuning guidance ship with the Melin Exchange Core." A visitor to this repo therefore cannot reproduce, or even inspect, a single number — `bench-results/` and `docs/plots/*` are both gitignored, and the two plots the gitignore exempts as "README-referenced" are not in fact referenced or tracked. Latency claims that can't be re-run get discounted to zero by exactly the buyers we want. Ship a load generator and harness in this repo driving `crates/examples/counter`, a `docs/benchmarking.md` with the hardware/kernel/tuning recipe (isolcpus, IRQ affinity, C-states, NIC settings), raw HDR histograms committed with the exact commit hash they came from, and the CDF plot inline in the README. Prerequisite for the DPDK-numbers item below, which currently has no public table to sit next to. |
| Set the BSL `Change Date` | Low | `LICENSE` carries the literal placeholder `Change Date: —`. The four-year fallback clause further down means the conversion is legally determined regardless, but a parameter block left unfilled is the first thing counsel reviewing the license sees, and it reads as unfinished. Set a concrete date per release and have `scripts/publish.sh` stamp or verify it as part of the release checklist, so it can't silently rot back to a placeholder on the next version. The date now lives in ten places — the root `LICENSE` plus a byte-identical copy in every published crate, so that each crate ships its own licence — and the tooling must update them in lockstep and fail if they differ. Run `scripts/publish.sh` in its default dry-run mode from CI while at it, so a broken manifest is caught before a release rather than during one. |
| Runnable quickstart: `counter-client` binary and demo cluster script | Low | `crates/examples/counter` starts a server and gives the reader nothing to talk to it with — the only working client is buried in `tests/round_trip.rs`, which already carries the full length-prefixed framing, Ed25519 challenge/response, and request/response tag handling. Promote that into a `counter-client` bin, add a README quickstart that is copy-pasteable end to end (keygen → server → client → observed response), and add a `scripts/demo-cluster.sh` that brings up a primary plus two replicas, drives load, and lets the operator `kill -9` the primary and watch auto-promotion complete. A five-minute failover that runs on a laptop is more persuasive to this audience than any latency table, and every piece of it already exists — this is packaging, not new capability. |
| Changelog and stability policy | Low | There is no `CHANGELOG.md`, and nothing states what `0.x` means for API breakage or how long a release is supported — an infrastructure dependency that won't say what changed between versions or when it will break you is one nobody can plan a deployment around. The MSRV third of this item has landed: `rust-version = "1.91"` in `[workspace.package]`, enforced by the post-merge `msrv` job on pushes to main, surfaced as a README badge (dynamic, reads crates.io — red "unknown" until the first publish that carries the field), with the bump policy in the root manifest promising release notes that do not exist yet. Add a `CHANGELOG.md` maintained per release (Keep a Changelog format), backfilled at least to the current release, a short versioning/support statement alongside it, and have `scripts/publish.sh` verify the version being published has an entry. |
| Pre-launch documentation set | Medium | Six gaps that a buyer's evaluator hits in the first hour, grouped because they are one writing pass and share an audience. **(a) Guarantees and failure modes** — durability-mode matrix, RPO/RTO, split-brain behavior under the raft control plane, and what happens on primary disk failure, network partition, or a lagging replica; the "Document the in-flight order contract on pipeline halt" item below is the RFP-facing half of this page and should land with it. **(b) Comparison and non-goals** — why Melin rather than Aeron, Chronicle Queue, a raw Disruptor, or Kafka/Redpanda, plus an explicit "when not to use Melin"; naming our own limits pre-empts the loudest objection and reads as confidence. **(c) A Correctness section in the README** — 780 test attributes, property tests, deterministic-replay and crash-recovery coverage, miri in CI, and a stated policy for the ~200 `unsafe` sites; the work is done and the README doesn't mention it. **(d) `SECURITY.md`** with a disclosure address, plus an auth doc — the Ed25519 `authorized_keys` format currently exists only as a comment in `counter/src/main.rs`. **(e) Licensing FAQ and pricing posture** — a plain-English can/can't-do summary, the rationale for BSL, and at minimum a pricing shape ("per-cluster annual, contact us"); BSL with no pricing signal stalls procurement before a conversation ever starts. **(f) A landing page with rendered docs** (mdBook) carrying the numbers and the design-partner CTA — a GitHub repo alone reads as a side project to anyone outside engineering. |
| Promoted-node journal catch-up before serving | Medium | The complete fix for the failover data-loss class the shipped peer-tip veto guards against (see `raft_promotion.rs`: a winner refuses to promote while a reachable peer advertises a higher journal tip, and the caught-up peer campaigns to take over), and what the mature systems in this space do (MongoDB catch-up, VSR state transfer): before opening its client listener, a promoted node asks surviving replicas for their journal tails beyond its own tip and applies the diff, so *any* election winner converges to the acked frontier. Strictly stronger than the veto: instead of steering promotion to the caught-up node, it repairs whichever node promotes — the veto/challenger handshake then becomes an optimization rather than the safety mechanism, and the one case the veto can only warn about (a caught-up peer that dies *after* the primary, leaving its higher tip unreachable) shrinks to the window before its tail was pulled. Also heals the `hybrid` case where a behind winner forces the caught-up replica's journal into a divergence archive. Cost is a new protocol role — a not-yet-promoted replica serving read-only journal tails on its already-bound replication port — with epoch fencing on that path (never serve a stale-epoch suffix) and mid-transfer failure handling; the existing `catch_up_from_journal` and streaming machinery is reusable, as is the shipped `PeerTips` tracking (it names the node to pull from). The replicated-mode failover test (`crates/core/server-runtime/tests/replicated_failover.rs`) is the regression harness. |
| Determinism test in the counter example (snapshot vs replay) | Low | The README tells application authors they "inherit determinism as long as their logic stays pure", and gives them nothing to check that with. Core has unit-level recovery tests, but no end-to-end assertion that the three ways of reaching a state agree, and `counter/tests/round_trip.rs` runs with `snapshot_interval_ms: 0`, so the reference application never exercises the shadow stage. Add a test that runs a node, drives a few hundred mixed requests over several connections, takes a snapshot mid-stream, keeps going, then compares three states: the live application (queried before shutdown), snapshot + tail replay, and full replay from genesis. Three-way rather than two-way so a mismatch points at its cause — snapshot serialization or application logic. Ship it as the template a `melin-app` implementor copies for their own application; it is also the concrete example behind the README's testing claims. Independent of everything else. |
| Pin the control-plane threads to the auxiliary core | Low | `raft-driver` (consensus loop + its current-thread tokio runtime), `raft-promotion` (auto-promotion watcher), and the replica health listener all float unpinned at `SCHED_OTHER` — the scheduler can place them on core 0, the IRQ core, adding jitter to NIC interrupt handling during elections / log replication bursts. The journal segment preparer just got a `PipelineCores` slot (`journal-prep`, tenth `--cores` entry) for exactly this reason; these threads should share that auxiliary core (all are >95% idle, so one core covers the lot) via an eleventh optional entry defaulting to the same core. Include the one-line hardening while there: `raft-promotion` lacks the defensive `clear_affinity` every other child-of-possibly-pinned-thread performs, so a future caller spawning it from a pinned context would confine it to a hot-path core. Surfaced during the journal fsync-beat fix (`docs/internal/journal-fsync-beat-2026-08.md`). |
| Publish DPDK numbers alongside kernel-TCP | Low | The README and current sales numbers are kernel-TCP only. Tier-1 TradFi venues all run on kernel bypass or specialized NICs — without DPDK figures the comparison is structurally incomplete and a buyer will discount the numbers accordingly. The DPDK transport already exists (server `dpdk` feature, `crates/exchange/bench/src/dpdk.rs`, exercised by `scripts/lan-bench-suite.sh`); this is harvesting numbers under the existing realistic flow generator and publishing them next to the kernel-TCP table in the README and `docs/benchmarking.md`. Pairs with the tick-to-trade decomposition below — without per-stage decomposition the DPDK win is reported as a black-box delta rather than attributable to NIC bypass. Independent of all engine work below. |
| Tick-to-trade decomposition in bench output | Medium | Today the bench reports full client-to-client round-trip latency. Exchange RFPs typically ask for the latency profile decomposed into NIC ingress → parse/decode → match → encode/respond → NIC egress, separately from the durability gate (journal + replication). The plumbing is partly there — `InputSlot::timestamp_ns` is captured at receipt and pipeline-stats tracks per-stage occupancy in aggregate — but per-request stage timestamps need to flow through the response path and into the bench histograms. Lets us report "gateway-to-match" the way CME / Nasdaq do, makes the kernel-TCP-vs-DPDK comparison from the item above attributable, and answers the most common diligence question without hand-waving. |
| Replicas pull configuration from primary | Medium | Today each node reads its own `ServerConfig` (instruments, fee schedules, auth keys, etc.) from local files; operators must keep the primary's and every replica's configs identical or replication diverges silently. Have the replica fetch the canonical config from the primary as part of the handshake, after auth but before journal catch-up — the replica only owns transport-level config (listen addr, replication addr, certs). Eliminates a silent-divergence class of incident and makes adding a replica a one-step operation. |
| Replicas refuse gateway connections with a primary-address redirect | Low | When a client (FIX gateway, bench, native TCP client) connects to a node that isn't currently the leader, the node should reject the handshake with a structured redirect carrying the current leader's order-entry address rather than silently accepting and then dropping orders, or rejecting with an opaque error. Add a `Redirect { primary_addr }` response variant and emit it from the auth path on any non-leader node; clients reconnect to the address in the frame. Closes the "ops accidentally pointed me at a replica" footgun on its own, and pairs with the shipped auto-promotion to give clients a clean follow-the-leader story across failover (replicas know the new leader as soon as Raft elects it; the next gateway reconnect lands in the right place automatically). Independent of the control plane — works today using static knowledge of the configured primary. |
| Revisit the `AppFactory` trait | Low | Once the full generification lift (PR-G/H/I) is in and exercised end-to-end on the trading binary plus at least one non-trading prototype, audit the trait surface for simplification. Candidates: drop `empty_for_seed` if no impl actually overrides it (its only reason to exist is the trading pre-sizing hint), fold `apply_operator_policy` into `empty`/`empty_for_seed` if no replication path genuinely needs the standalone reapply, or replace the `Vec<Event>` return of `seed_events` with an iterator if any factory ends up materialising a large seed set. Cheap pass that we couldn't make confidently during the refactor because we only had one implementor — revisit after a second one exists. |
| Offline journal inspector (`melin-admin journal-info`) | Low | The cluster-wide outage recovery playbook in `docs/replication.md` ("Cluster recovery") requires determining each node's journal end sequence by booting it briefly in `--standalone` mode and reading `journal_sequence` from `/healthz`. That's a serial boot/stop loop across every surviving node, with the side risk that an inspection node accidentally accepts client traffic or replication during the window. Add a read-only `journal-info` subcommand to the existing `melin-admin` binary (`crates/exchange/admin/src/main.rs`) that opens the journal directory directly via the existing reader (`crates/core/journal/src/reader.rs`) and prints, per node, the last sequence, the tip chain hash, and the last entry timestamp — enough to pick the longest-journal node as the new primary without starting a server process. Pairs with the recovery procedure in `docs/replication.md`; independent of all engine work above. Listed as a wishlist item in the replication doc's Limitations section — this promotes it to its own roadmap line. |
| Owned-buffer io_uring layer (kernel loans become moves) | Medium | The io_uring use-after-free class fixed across the replication sender, the replication receiver, and the client-facing reader (`crates/core/server-runtime/src/uring_teardown.rs` carries the shared teardown policy) had one root cause: buffers are *borrowed* to the kernel through `unsafe` SQE pushes, so the borrow checker's view ends where kernel ownership begins, and the discipline lives in SAFETY comments promising temporal invariants — four of which were wrong. No tool we run can see the class: ASan/TSan instrument CPU accesses (a kernel-side store into freed heap passed six ASan runs), and Miri cannot execute io_uring. Make the type system tell the truth instead, on the model tokio-uring/ringbahn established: a ring wrapper where submitting an op *moves* the buffer (or a move-only pool-lease token) into an in-flight ledger keyed by `user_data`, completions hand it back, and `Drop` runs the wake-then-bounded-drain-then-leak quiesce fed by the ledger — so freeing a kernel-held buffer, forgetting the quiesce, miscounting in-flight ops, or double-recycling a pool bid stops compiling rather than needing review. The `unsafe` concentrates into one audited module pinned by the existing socketpair tests; kernel-semantics assumptions (F_MORE terminality, shutdown-completes-RECV) stay test-verified. Migrate one transport at a time — sender first (smallest surface, freshest tests), then receiver (multishot + provided pool leases), then the reader (per-connection arms over the shared pool). Ledger is a fixed slab indexed by the `user_data` already assigned, moves are pointer copies — expected hot-path delta is noise, but benchmark before/after. Include the two detection layers that catch the class independent of the abstraction: a teardown-churn soak (connect/traffic/kill cycles across every ring-owning thread) and a test-profile quarantine allocator (delayed free + canary check) that turns a late kernel write into a deterministic failure; and fold the temporal-SAFETY grep (`outlives`/`until the CQE`/`stays alive` inside `unsafe` justifications) into the lockstep-confession audit below. Safety-slice prerequisite of the deferred "Unified transport abstraction over io_uring and DPDK" item, not a competitor to it. |
| Migrate the control plane to openraft 0.10 (once stable) | Medium | The 0.9 line draws each node's election timeout **once** at startup and campaigns on a fixed tick grid, which forced three in-tree compensations, each labeled as such at its definition: the deterministic per-node heartbeat offset in `melin-raft`'s driver (aligned-grid split votes), the election stand-down in `raft_promotion.rs` (a tip-behind replica re-winning doomed leaderships indefinitely, because the depose/re-elect race between fixed timeout draws has a fixed winner — observed livelocking failover past a 60 s deadline in ~5% of runs before the fix), and the challenger nudge's hold-down. The 0.10 line re-randomizes the timeout per election round (`do_elect` → `resample_election_timeout`) and adds pre-vote, removing the livelock class at the source: the migration deletes the heartbeat-offset workaround, likely the hold-down, and demotes the stand-down and the journal-tip vote filter from load-bearing to defense-in-depth. Blocked on upstream — 0.10 is alpha-only as of 2026-08 with weekly alpha releases, and pinning an alpha under the consensus control plane of a commercial product is not acceptable; act when a stable 0.10 ships. Storage and API surface changes make it a real migration, not a version bump; the replicated-failover batch harness (`tests/replicated_failover.rs`, run in the hundreds) is the acceptance gate. |
| Type the replica cursors in the durability gate (`WireSeq` through `ReplicationMetrics`) | Low | The gate's local `persisted` cursor is `WireSeq`-typed end-to-end, but `evaluate_durability` still flattens it into a raw `[[u64; 2]; 3]` cursor view alongside the untyped `ReplicationMetrics` gauges (`acked_sequence` / `in_memory_sequence` — the `Ack` frame's wire-seq fields, stored in the same group as the slot-acked quorum cursors). A wrong-space value wired into the view compiles silently today. Add `WireSeq`-typed accessors on `ReplicationMetrics` and carry the type through `connected_persisted_min` and the policy `CursorView` boundary. Completes the typing the `PipelineCursors` work deliberately stopped short of at the gate's multi-cursor view. |
| Unify sequence allocation (delete the wire-seq shadow) | Medium | The matching stage shadows the journal stage's sequence allocator instead of sharing one allocation point — the per-event skip rule is mirrored in two places with comments promising lockstep. v14 removed two of the three divergence sources (Checkpoint, GenesisHash) and five tests now pin the agreement (rule-table, rotation, recovery, replica-side, and the frozen-replica gate-stall integration test), so this is no longer an active bug factory — but the residual risk is concrete: a future `JournalEvent` variant with asymmetric allocate/skip rules drifts silently, because no test can feed an event kind that doesn't exist yet. Replace the shadow with a single allocation point (candidates: derive the sequence from the disruptor slot index, or allocate at publish) so the lockstep contract is deleted rather than tested. Hot-path design change — treat as a deliberate redesign, not opportunistic cleanup. **Trigger: must land before (or together with) the next `JournalEvent` variant.** Builds on the `PipelineCursors` cursor-space naming, which has landed. |
| Lockstep-confession audit | Low | The v14 bug factory had a recognizable signature: derived state maintained in parallel at a distance, with comments promising manual lockstep ("mirrors X exactly — any drift would re-introduce…"). A grep for `mirrors\|must match\|kept in sync\|stays aligned\|lockstep\|same rule as` across `crates/` finds **124 non-test hits** beyond the sites covered by the typed-cursor and sequence-allocation items above — and those came from one session's incidental reading, not a survey. Triage each hit into: benign (match-exhaustiveness notes), already pinned by a test, or v14-shaped (separately-updated state across threads/crates whose agreement nothing asserts). Output is a prioritized backlog feeding future roadmap items, plus tests or owning-module refactors for the third bucket. Cheap, bounded, and the highest-leverage way to find the next vacuous-gate-class bug before a customer does. Independent of all other roadmap work. |
| Document the in-flight order contract on pipeline halt | Low | The persist-before-ack gate (`crates/core/transport-core/src/pipeline.rs:746-750`) guarantees no client is acked for an event that isn't durable on disk (and on a replica's disk, per the active durability mode). What is **not** documented is the symmetric contract for orders that were submitted but never acked: when the journal stage exits on disk failure, the response stage cannot advance past the failed batch and in-flight responses never go out — clients see only a TCP RST when the process exits. There is no structured `JournalUnavailable` reject. The reconciliation contract is currently implicit: an order whose connection dropped mid-flight may have been (a) not journaled — safe to retry; (b) journaled and matched but never acked — exchange state has already advanced, must not retry blindly; or (c) journaled but not yet matched — will be deterministically replayed on primary restart. Clients have to reconcile via account state on reconnect to disambiguate. Today this is inferable only from reading the pipeline source. Exchange RFPs ask for it in writing. Add a section to `docs/journal.md` (or a new `docs/client-recovery.md`) that spells out the contract with worked examples, and cross-link from `docs/replication.md`. No code change. Independent of all other roadmap work. |
| Split replication off the DPDK client poll thread | Medium | On the DPDK path the replication driver runs **inline on the client poll loop**: `DpdkReplicationDriver::tick` is invoked from the same `dpdk_transport.rs` iteration that drains client responses to the wire and pulls client order packets off the NIC (`transport.poll()`), and the replication listener deliberately shares the trading queue (`server.rs`: the poll thread "accepts both trading and replication connections off the same queue"). This couples replication and the client hot path in **both directions**. **(a) Clients starve replication:** under heavy client load the replication sender doesn't get enough cycles to drain the ring, it fills, and a healthy replica is evicted. **(b) Replication stalls clients:** a replica handshake runs journal catch-up / snapshot transfer, and the catch-up→live handoff back-fill (`bridge_catchup_to_live`, bounded by `HANDOFF_BRIDGE_TIMEOUT`), inline on this poll thread — so for that duration the thread stops ingesting orders and sending acks for the clients on its queue. The matching/journal/response stages run on their own cores and keep processing already-ingested work; it is the NIC-facing RX/TX on the shared poll thread that pauses. Bounded today — the handoff spin is capped at 30 ms (typically microseconds on PLP+xfs), catch-up is the larger but pre-existing stall, and the kernel-TCP path is unaffected (each replica gets its own handler thread) — so **not urgent**. Fix: give replication its own core — a separate smoltcp socket set on a dedicated DPDK queue, or a shared-nothing handoff from the client poll thread — preserving the single-writer invariant on the replication ring (consumer side only). Promote when DPDK dual-replica reconnect latency becomes a diligence concern. Surfaced by the `perf/handoff-deterministic-close` review; promotes the former "Split the DPDK poll thread" optimization item with the replication-blocks-clients direction added. |

## DPDK Transport Optimization

| # | Optimization | Est. impact | Complexity | Description |
|---|-------------|------------|------------|-------------|
| 1 | Bypass smoltcp on hot path | Significant latency | Very high | For connected+authenticated clients, parse TCP directly from raw Ethernet frames. Eliminates smoltcp's per-packet overhead (neighbor lookup, socket dispatch, congestion window, timer checks). Custom minimal TCP for steady-state data path only. |
| 2 | Unified transport abstraction over io_uring and DPDK | Moderate maintainability, moderate latency | High | The TCP (io_uring) and DPDK code paths have independent replication senders, response writers, and connection handlers with duplicated logic that drifts (e.g. the journal-recreate-on-reconnect bug was fixed in TCP but not DPDK). Investigate a transport trait that captures the common interface (accept, connect, send, recv, poll) so the replication protocol, response stage, and connection state machine can be written once. The challenge is that io_uring is completion-based (submit SQE, reap CQE) while DPDK/smoltcp is poll-based (call poll, check buffers) — the abstraction must not penalize either model. |

## Deferred

Features with limited near-term value. Will revisit when the core product is mature or a specific buyer requires them.

| Feature | Why deferred |
|---------|-------------|
| SPDK journal | Userspace NVMe driver for journal writes. Bypasses kernel block layer entirely. TCP pipelining already hides fsync latency (fsync and no-persist throughput converged at ~8M/s), so the kernel block layer is no longer a bottleneck. High complexity, minimal expected gain. |
| io_uring journal writes | Shipped and then retired with the O_DIRECT sector writer: the journal stage used to submit `WRITE+RWF_DSYNC` async via io_uring, reaping CQEs non-blocking while encoding the next batch, with `IORING_OP_WRITE_FIXED` against registered batch buffers. The buffered writer is the only writer now, and its write path is being split across a dedicated disk thread instead. Revisit an io_uring backend only behind that thread's seam, and only if a trace shows the synchronous `pwrite`/`fdatasync` pair is the binding cost — note io-wq workers are anonymous, which breaks the thread-targeted off-CPU tracing every journal diagnosis here has depended on. |
| Vectored journal writes | Encode each event into its own stack buffer, pass as iovec array to `pwritev2`. Eliminates memcpy-per-event into the batch buffer. Small gain (~1-2µs/batch). |
| Verbatim byte-path journaling | Write the primary's encoded journal bytes directly on both primary and replica, skipping the decode/re-encode step on the replica side and an encode-from-struct pass on the primary. Saves CPU and reduces journal-stage work on the replay-critical path. Attempted once as a replica-only optimization (branch `replica-verbatim-journal`) but created an asymmetry that diverged fsync batching behavior between primary and replica — reverted in favor of a symmetric decode/re-encode on both sides. Revisit only with a plan to apply it on both sides simultaneously, preserving per-fsync size bounds. |
| io_uring RECVSEND_FIXED_BUF | `IORING_RECVSEND_FIXED_BUF` for registered buffer recv/send. Returned EINVAL on kernel 6.8; should work on 6.10+. Also test `IORING_RECVSEND_BUNDLE` for batched recv. Est. 15-25% throughput. |
| Dual-NVMe journal hedging | Two journal threads on separate NVMe drives, response stage gates on the fastest. Cuts tail latency from P(slow) to P(slow)². Free durability redundancy. Low complexity but requires a second NVMe slot. Revisit when journal fsync is the dominant tail contributor. |
| AF_XDP transport | DaMoN '25 found AF_XDP disappoints vs DPDK for small-message request-response workloads. DPDK transport already in progress. Revisit if DPDK proves insufficient. |
| Chain replication | Chain replication (primary → replica A → replica B) reduces primary fan-out. Dual parallel replication (up to 2 replicas) is implemented; chain topology is deferred. |
| TLS | Most exchange deployments use VLAN instead. Only needed for compliance-driven buyers. |
| Hybrid UDP multicast + TCP recovery for event channel | Current event channel is pure TCP. Multicast would reduce latency for co-located subscribers but adds complexity (gap detection, retransmit). Defer until a buyer needs sub-microsecond market data. |
