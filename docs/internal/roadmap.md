| A replica that falls behind at full rate cannot rejoin, and a new history serves before its replicas are live | Medium | Found by bisecting a 6% throughput loss and a doubled p99.9 tail in Exchange Core's dual-replica TCP benchmark (`lan-bench-suite.sh`, `tcp-dual-repl`, 4 clients × window 56, ~1M orders/s): clean through e063af30, regressed from 83d14a32 (genesis journaled at creation). The primary's health samples and logs show what the bench numbers hide: the second replica is evicted for ring backpressure within two seconds of load starting (`replication ring full — evicting replica (would create sequence gap)`, then `evicting slow replica (ring backpressure timeout)`), reconnects, catches up from the journal, is evicted again at the handoff, and loops — 420 evictions in a 60 s run, `melin_replica_catching_up{slot="1"}` set in 63 of 69 samples. The ack policy (`persisted>=1 && in_memory>=2`) stays satisfied by the replica that held, so the run passes while the primary reads its own journal for catch-up against its own writes; that is the tail. Two defects underneath, both older than the commit that exposed them. (1) The replication ring is sized in slots (`--replication-ring-size`, 256, documented as 128 MiB), one batch per slot whatever its size: at the bench's batch sizes it holds ~57K entries, ~57 ms at 1M/s, so a stall of that length evicts a healthy replica, and once evicted the journal catch-up (disk-bound, seconds) can never close a gap the ring refills in tens of milliseconds, so `bridge_catchup_to_live` cannot converge at rate. Fix: size the ring by bytes or entries (fill a slot across consecutive small batches), so the buffering is the documented one; keep the slot inactive until the bridge is within ring reach of the live tail, and evict only a replica that cannot sustain the steady-state rate. Consider backpressure instead of eviction when the evicted replica is one the ack policy counts on. (2) A new history waits for its *first* replica only (`new history: waiting for the first replica before serving clients`, logged next to `ack policy starts degraded`): before 83d14a32 the genesis streamed through the pipeline for ~4 s after that and the second replica was warm and live before clients arrived; now it catches up from the journal and goes live cold a second before full load. Fix: wait until the ack policy's in-memory target is met by caught-up replicas before serving a new history. With the bench suite made to wait for both replicas to be live before loading, the same build measures at baseline (1.03M/s, p99.9 337 µs, no evictions), which confirms (2) as the trigger and (1) as the reason it does not heal. Reproduction: Exchange Core at `chore/melin-main-bump` or later, `TRANSPORTS=tcp-dual-repl WORKLOADS=throughput ./scripts/lan-bench-suite.sh …`; the suite now gates on live replicas and fails a run with evictions, so the regression is visible as a failed run rather than a few percent. Reproduced on 2026-10-15 with this repo's suite (`lan-bench-suite.sh ec`, kernel TCP, 4 × 56, ~1.37M orders/s, four EPYC 9275F hosts). "Both replicas live" (connected, none catching up) is not enough: a replica that has just finished its catch-up is still cold. With load starting ~1.3 s after the second replica went live, every run evicted a replica less than a second into the load, at sequence ~1.18–1.20M every time, and the rejoin then looped for the rest of the run (8–20 evictions per run, six runs out of six). Five seconds between both replicas live and the load (`SETTLE_SECS=5`) removed every eviction, with the same distribution as the Exchange Core's suite, whose `sleep 1` before each replica launch leaves ~2 s and never evicted (three runs out of three). So (2) needs a stronger readiness condition than "caught up", which the fix should define and the health endpoint should expose. The evicted replica was 65,657 entries behind: 256 slots of ~256-entry batches, ~4.5 MB of the nominal 128 MiB, ~48 ms at that rate. `--replication-ring-size 4096` absorbed the cold start too (no evictions), at a p99.99 of 3.4 ms against 0.4 ms for a settled run, so it is not a substitute for the readiness fix. One more symptom for the fix to cover: after each rejoin, the evicted replica resumed further behind the point it was evicted at (0.07M, 0.26M, 1.4M, 2.3M, then 24M entries), and it stopped adopting rotations while streaming live. So after a rejoin it is its persisted position, not only the ring, that fails to keep up. The fix lands with a test that evicts a replica under a full ring at batch sizes well below a slot and sees it rejoin and stay. |

| Document the in-flight order contract on pipeline halt | Low | The persist-before-ack gate (`crates/core/transport-core/src/pipeline.rs:746-750`) guarantees no client is acked for an event that lacks the copies the active ack policy demands (one or two fsynced copies, and/or a second in-memory copy). What is **not** documented is the symmetric contract for orders that were submitted but never acked: when the journal stage exits on disk failure, the response stage cannot advance past the failed batch and in-flight responses never go out — clients see only a TCP RST when the process exits. There is no structured `JournalUnavailable` reject. The reconciliation contract is currently implicit: an order whose connection dropped mid-flight may have been (a) not journaled — safe to retry; (b) journaled and matched but never acked — exchange state has already advanced, must not retry blindly; or (c) journaled but not yet matched — will be deterministically replayed on primary restart. Clients have to reconcile via account state on reconnect to disambiguate. Today this is inferable only from reading the pipeline source. Exchange RFPs ask for it in writing. Add a section to `docs/journal.md` (or a new `docs/client-recovery.md`) that spells out the contract with worked examples, and cross-link from `docs/replication.md`. No code change. Independent of all other roadmap work. |

| Monotonic sequencer time, derived from the journal | Medium | The application's clock is assembled from pieces that each hold a different invariant, and they have drifted apart. The tick generator clamps each tick only against the previous *tick* (`transport-core/src/tick.rs`), and its last value resets when the reader starts. Event timestamps are stamped at ingress and can arrive out of order (the "rare producer race" `dispatch.rs` documents). `dispatch` advances `Application::tick` through a watermark for event timestamps but calls it *unconditionally* for journaled ticks, so every tick fires `tick` twice and a tick below the watermark moves the application's clock backwards — after an NTP step, after that producer race, or after a failover to a node whose clock is behind. Worse, the watermark is per-process state, not derived from the journal: it starts at 0 in the live matching stage at boot even after replay (`pipeline.rs`), on snapshot restore (`journaled_app.rs`) and in the shadow stage (`shadow.rs`). So a primary restarting after a clock step back calls `tick` for events that a continuously-following replica skips, and a snapshot taken inside such a window restores to a node that makes calls the live one did not — the same journal driving different application state on different nodes, with nothing to detect it (the hash chain covers the journal's bytes, not the application's state). Rare, since it needs a clock regression across a restart, snapshot or failover, but it is exactly the silent divergence the product promises cannot happen; the exchange's `tick`, for one, stamps the clock its rate limiter reads, so it is not idempotent against a rewind. A one-line guard on the tick path fixes the double call and the backwards tick but not the watermark reset, and would read as solved. Direction: **the sequencer assigns time the way it assigns sequence — strictly monotonic by construction.** Every timestamp a primary issues, tick or event, is clamped against one last-issued value seeded from the recovered journal tail at boot and at promotion; journaled timestamps are then strictly increasing on disk, replicas inherit them from the primary's stream, the dispatch watermark stops being state (an assertion, not a variable), and `ApplyCtx::now_ns` becomes monotonic too, which settles whether `apply` may assume increasing timestamps. The design question is the producers other than the reader — startup events, the promotion epoch bump, the DPDK poll thread — which must share or be ordered against that one value. Afterwards restore the strong contract in `Application::tick`'s rustdoc (weakened to "may repeat or go backwards" to match today's behavior). Acceptance: tests for a restart across a clock step back, a snapshot inside a regression window and a failover to a slower clock, each asserting the same `tick` sequence on every path — the counter determinism test above is the natural harness. Changes replayed behavior, so it needs a journal format change: landing it in the release that already moves to format 15 costs no extra migration; after that it carries its own. Plan: [monotonic-sequencer-time-2026-09.md](monotonic-sequencer-time-2026-09.md). |
| Record the application's event-encoding version in the journal | Medium | A snapshot carries `APP_VERSION` and is refused on mismatch, but journal entries carry no application version at all: every replay — restart, replica catch-up, failover — decodes old entries with whatever `AppEvent::decode` the running binary has. An upgrade that changes an event's layout and still decodes the old bytes replays a *different* history with no error; one that fails to decode surfaces as `CorruptEntry` mid-replay or mid-stream, on a replica, long after the deploy. For a product sold on exact replay and a regulatory audit trail this is the worst failure shape, and today only operator discipline prevents it (`docs/journal.md`, "Changing the Application's Encoding"). The encoding, its versioning and its migrations stay the application's; what only the runtime can do is *detect* a mismatch at the points where it matters. Melin decides which binary decodes which bytes (replay, catch-up, failover), so it alone can refuse before replay starts, and the replication handshake is the only place both sides of a rolling upgrade are visible. An application cannot do either from inside `decode`: a version byte in its own events, or a version marker it journals at startup, finds the mismatch only when replay reaches it, and cannot refuse a replica. The snapshot side already draws the line here (`APP_VERSION`). Options: **(1)** a per-segment version: the application declares an event-encoding version and the oldest one it can still decode, which the runtime compares but never interprets; every segment header records the version that wrote it (journal format bump); a node refuses to open a segment outside that range before replaying anything, rotates to a fresh segment when it starts under a new version so no segment mixes two, and the replication handshake compares versions so a replica that cannot read the primary's stream is refused at connect rather than failing mid-stream; **(2)** a version byte per entry: finer-grained but pays per event for what only changes at upgrades; **(3)** documentation only, the status quo. Recommend (1). Exact match alone would not do: an upgraded node could not open the segments its previous version wrote. Decoding older versions stays the application's job; the runtime only enforces the range it declares. Declare both as associated constants with defaults (0, "unversioned"), so existing applications compile unchanged and opt in by overriding them. Decide alongside it whether snapshot `APP_VERSION` and the event version stay separate (they change for different reasons) and whether the snapshot check should accept a readable range too: today it is exact-match, which leaves a snapshot-layout change with no in-place upgrade path short of an external converter or replay from genesis. Not breaking for applications, but breaking for journal files and for the replication protocol, so it should land before applications outside this repo accumulate journals, ideally in the release that already bumps the format for "Monotonic sequencer time"; the application guide's upgrade section depends on it. |
| Degraded acks on a halted node: what is left | Medium | Degraded acks and the `ACK-POLICY disk` halt override are built (see the plan): once a primary halted by losing its last replica has been halted for `--degraded-ack-grace-ms`, it answers each held reply, write or query, as soon as its own journal holds it, ending in `BatchEndDegraded`, and a journaled policy change released that way waits, pending, for the policy before it. What remains: **The `disk` query hang is not root-caused.** The Exchange Core reproduced queries hanging on a primary halted under `ack-policy disk` (primary + one replica, replica SIGKILLed, idle node), where the primary's own journal should confirm every reply. The step-1 test does not reproduce it on kernel TCP or on DPDK, at load or idle, ticks on or off; degraded release does not apply under `disk`, so if the bug is real it survives this work. Next: run it against the Exchange Core's own reproduction (SIGKILL, their query types). **Counting presence from a replica's first ack.** A replica the primary accepts and that then refuses the stream (stale primary, lineage mismatch, divergence) counts from the handshake until its socket closes, so each retry lifts the halt for that moment: writes taken then wait in the gate for a copy that never comes, and hold every later reply until degraded release answers them a grace period after the replica leaves. A replica ack on accepting `StreamStart` (a replication protocol change, left open in the journaled ack-policy plan) removes the window, and lets a replica that joins at the tip of an idle primary, or leaves mid-catch-up, end the forced-`disk` override too; today only a first ack on the live stream does, and replicas never ack heartbeats. | Promoted-node journal catch-up before serving | Medium | The complete fix for the failover data-loss class the shipped peer-tip veto guards against (see `raft_promotion.rs`: a winner refuses to promote while a reachable peer advertises a higher journal tip, and the caught-up peer campaigns to take over), and what the mature systems in this space do (MongoDB catch-up, VSR state transfer): before opening its client listener, a promoted node asks surviving replicas for their journal tails beyond its own tip and applies the diff, so *any* election winner converges to the acked frontier. | Owned-buffer io_uring layer (kernel loans become moves) | Medium | The io_uring use-after-free class fixed across the replication sender, the replication receiver, and the client-facing reader (`crates/core/server-runtime/src/uring_teardown.rs` carries the shared teardown policy) had one root cause: buffers are *borrowed* to the kernel through `unsafe` SQE pushes, so the borrow checker's view ends where kernel ownership begins, and the discipline lives in SAFETY comments promising temporal invariants — four of which were wrong. No tool we run can see the class: ASan/TSan instrument CPU accesses (a kernel-side store into freed heap passed six ASan runs), and Miri cannot execute io_uring. Make the type system tell the truth instead, on the model tokio-uring/ringbahn established: a ring wrapper where submitting an op *moves* the buffer (or a move-only pool-lease token) into an in-flight ledger keyed by `user_data`, completions hand it back, and `Drop` runs the wake-then-bounded-drain-then-leak quiesce fed by the ledger — so freeing a kernel-held buffer, forgetting the quiesce, miscounting in-flight ops, or double-recycling a pool bid stops compiling rather than needing review. The `unsafe` concentrates into one audited module pinned by the existing socketpair tests; kernel-semantics assumptions (F_MORE terminality, shutdown-completes-RECV) stay test-verified. Migrate one transport at a time — sender first (smallest surface, freshest tests), then receiver (multishot + provided pool leases), then the reader (per-connection arms over the shared pool). Ledger is a fixed slab indexed by the `user_data` already assigned, moves are pointer copies — expected hot-path delta is noise, but benchmark before/after. Include the two detection layers that catch the class independent of the abstraction: a teardown-churn soak (connect/traffic/kill cycles across every ring-owning thread) and a test-profile quarantine allocator (delayed free + canary check) that turns a late kernel write into a deterministic failure; and fold the temporal-SAFETY grep (`outlives`/`until the CQE`/`stays alive` inside `unsafe` justifications) into the lockstep-confession audit below.
