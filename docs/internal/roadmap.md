# Roadmap

Planned features sorted by value/complexity ratio for commercial readiness.

## Active

Sequenced by dependency and priority — items higher up are unblocked
and ship first, items further down build on what came before.

The first three items gate the public release and announcement: they are
what a first-time visitor — or a buyer's technical evaluator — checks
before anything else, and every one of them is currently missing or
broken in the public repo.

| Monotonic sequencer time, derived from the journal | Medium | The application's clock is assembled from pieces that each hold a different invariant, and they have drifted apart. The tick generator clamps each tick only against the previous *tick* (`transport-core/src/tick.rs`), and its last value resets when the reader starts. Event timestamps are stamped at ingress and can arrive out of order (the "rare producer race" `dispatch.rs` documents). `dispatch` advances `Application::tick` through a watermark for event timestamps but calls it *unconditionally* for journaled ticks, so every tick fires `tick` twice and a tick below the watermark moves the application's clock backwards — after an NTP step, after that producer race, or after a failover to a node whose clock is behind. Worse, the watermark is per-process state, not derived from the journal: it starts at 0 in the live matching stage at boot even after replay (`pipeline.rs`), on snapshot restore (`journaled_app.rs`) and in the shadow stage (`shadow.rs`). So a primary restarting after a clock step back calls `tick` for events that a continuously-following replica skips, and a snapshot taken inside such a window restores to a node that makes calls the live one did not — the same journal driving different application state on different nodes, with nothing to detect it (the hash chain covers the journal's bytes, not the application's state). Rare, since it needs a clock regression across a restart, snapshot or failover, but it is exactly the silent divergence the product promises cannot happen; the exchange's `tick`, for one, stamps the clock its rate limiter reads, so it is not idempotent against a rewind. A one-line guard on the tick path fixes the double call and the backwards tick but not the watermark reset, and would read as solved. Direction: **the sequencer assigns time the way it assigns sequence — strictly monotonic by construction.** Every timestamp a primary issues, tick or event, is clamped against one last-issued value seeded from the recovered journal tail at boot and at promotion; journaled timestamps are then strictly increasing on disk, replicas inherit them from the primary's stream, the dispatch watermark stops being state (an assertion, not a variable), and `ApplyCtx::now_ns` becomes monotonic too, which settles whether `apply` may assume increasing timestamps. The design question is the producers other than the reader — startup events, the promotion epoch bump, the DPDK poll thread — which must share or be ordered against that one value. Afterwards restore the strong contract in `Application::tick`'s rustdoc (weakened to "may repeat or go backwards" to match today's behavior). Acceptance: tests for a restart across a clock step back, a snapshot inside a regression window and a failover to a slower clock, each asserting the same `tick` sequence on every path — the counter determinism test below is the natural harness. Changes replayed behavior, so it needs a journal format change: landing it in the release that already moves to format 15 costs no extra migration; after that it carries its own. |
| Record the application's event-encoding version in the journal | Medium | A snapshot carries `APP_VERSION` and is refused on mismatch, but journal entries carry no application version at all: every replay — restart, replica catch-up, failover — decodes old entries with whatever `AppEvent::decode` the running binary has. An upgrade that changes an event's layout and still decodes the old bytes replays a *different* history with no error; one that fails to decode surfaces as `CorruptEntry` mid-replay or mid-stream, on a replica, long after the deploy. For a product sold on exact replay and a regulatory audit trail this is the worst failure shape, and today only operator discipline prevents it (`docs/journal.md`, "Changing the Application's Encoding"). Options: **(1)** a per-segment version — the application declares an event-encoding version (plus, optionally, the oldest it can still read, so adding an event kind does not force a snapshot migration); every segment header records the version that wrote it (journal format bump); a node refuses to open a segment it cannot read before replaying anything, rotates to a fresh segment when it starts under a new version so no segment mixes two, and the replication handshake compares versions so a replica that cannot read the primary's stream is refused at connect rather than failing mid-stream; **(2)** a version byte per entry — finer-grained but pays per event for what only changes at upgrades; **(3)** documentation only — the status quo. Recommend (1). Decide alongside it whether snapshot `APP_VERSION` and the event version stay separate (they change for different reasons) and whether the snapshot check should accept a readable range too — today it is exact-match, which leaves a snapshot-layout change with no in-place upgrade path short of an external converter or replay from genesis. Breaking for every application and for journal files, so it should land before applications outside this repo accumulate journals; the application guide's upgrade section depends on it. |
| Application-defined client roles | Medium | The permission model in `melin-app` (`auth.rs`) is the exchange's separation of duties baked into the generic runtime: every key maps to one of `operator`, `trader`, `custodian`, `readonly`, `replication`, with `can_trade()` / `can_manage_funds()` helpers. The runtime itself acts on only two — `operator` gates the admin endpoint, `replication` authenticates replicas; `trader`, `custodian` and `readonly` mean something only to the exchange's decoder. Every other application has to squeeze its access model into trading roles — the echo and notary examples already fall back to "anything but `readonly` / `replication` may write" — and one with roles of its own (a payments system's payer and auditor) cannot express them at all; an evaluator reading `Permission::Trader` in a generic sequencer's API sees a trading engine with the business logic taken out. Options: **(1)** the application declares its roles — the runtime keeps the two it acts on, the application supplies an associated role type parsed from the `authorized_keys` role token (the runtime parsing its own tokens first), and the decoder receives `Permission<Role>` (`Operator`, `Replication`, or `App(role)`); typed, fits any domain, and existing key files keep working once the exchange declares `trader` / `custodian` / `readonly` itself; costs one associated type threaded through `RequestDecoder` and the server builder, and the exchange's migration; **(2)** the application names its roles as strings and the decoder gets an index into that list — less machinery, but nothing type-checks a role the decoder matches on; **(3)** a fixed neutral set (`writer`, `reader`, …) — cheapest, still one access model imposed on every application. Recommend (1). Breaking for every application's decoder, so like the event-encoding version it is cheapest before applications outside this repo are written against the current API. |
| Halt refusals behind a stalled ack gate | Medium | A halted node refuses client writes at ingress and the response stage delivers the rejection (`crates/core/server-runtime/src/halt.rs`). That stage is one thread that waits inside the durability gate on each reply until the ack policy confirms it, so under a policy that needs a replica the first reply in flight when the last replica leaves parks the stage until a replica returns or the operator swaps the policy — and every refusal queued after it waits the whole halt. Under `disk`, or when the halt lands on an idle node, refusals go out at once; under `disk+ram` / `two-disks` at load the client gets the silence and timeout the refusal was designed to spare it. Correctness is unaffected: the refused write is never journaled, and the rejection does go out when the gate opens. What is held at that moment is not lost either — the writes behind the gate are journaled on the primary (often fsynced) but lack the replica copy the policy demands, so they must not be acked yet and will be, or will be replayed, once the cluster heals; the design has to keep that distinction, and the client-facing contract for it belongs with the "in-flight order contract on pipeline halt" item below. Options: **(1)** doc-only — a refusal cannot overtake a reply the gate holds, and `ACK-POLICY disk` releases everything at once; **(2)** per-connection release from inside the gate wait — the reader stamps each refusal with its connection's own write count, the stage tracks per-connection answered counts, and the gate loop's degraded path syncs the queue and sends refusals for connections with nothing older unanswered (send buffers are clean at gate-wait time since nothing is appended before the gate opens); costs state on both sides of the queue and a second reason to send mid-batch; **(3)** a response stage that parks a gated reply per connection and keeps serving the others — the general fix, but a redesign of the in-order single-cursor hot path, and under a replica-less policy nothing is confirmable anyway, so it frees only refusals and queries. `docs/replication.md` currently says the rejection "does not wait on the ack policy", which holds only for (1)'s narrow cases until this is decided. |
| Answer queries on a halted node | Medium | A primary halted by losing its last replica refuses writes correctly but never answers a query: the reply is not delayed, it is withheld until a replica returns, and the client sees only its own read timeout — indistinguishable from a dead network, so a halt that loses nothing still turns into timeouts, retries and reconnects across every client, at exactly the moment operators and traders want positions. Reproduced by the Exchange Core on a primary + one replica with the replica SIGKILLed, on melin 0.15.0, 0.16.0 and `main` at `84d1b0eb` (ingress refusal): the write is rejected with `ReplicaDisconnected`, `QueryStats` and the request-sequence query hang (killed after 5 min), and `/healthz` / `/metrics` keep answering throughout. Not a regression. Withholding non-durable state from a query is right — a reply can reveal an event a failover would erase — but while halted almost nothing is non-durable: since ingress refusal, the only events a halted node still journals are its own scheduler ticks (`journal_sequence` climbs ~4/s while halted), and every query reply is gated behind them (`slot_needs_gate` applies to every slot). That explains `ram` / `disk+ram` / `two-disks`, but **the hang also reproduces under `ack-policy disk`**, where the primary's own journal should confirm those ticks — so there is a second, unidentified cause; root-cause it first, it may be a gate that never re-evaluates on a tick-only batch rather than a policy question. Options: **(1)** stop generating ticks while halted — the application state then equals the replicated prefix, query replies pass the gate at once and are fully safe; time-driven work (GTD expiry, schedules) pauses and catches up on the first tick after resume, deterministically since resumed ticks are journaled as usual, and nothing trades during a halt so pausing costs nothing; **(2)** refuse queries at ingress while halted — trivial and fails fast, but leaves a halted venue blind to positions; **(3)** serve queries from the durable-prefix state the shadow stage already maintains — no pause, but a second read path. Recommend (1) once the `disk` case is understood. |
| Promoted-node journal catch-up before serving | Medium | The complete fix for the failover data-loss class the shipped peer-tip veto guards against (see `raft_promotion.rs`: a winner refuses to promote while a reachable peer advertises a higher journal tip, and the caught-up peer campaigns to take over), and what the mature systems in this space do (MongoDB catch-up, VSR state transfer): before opening its client listener, a promoted node asks surviving replicas for their journal tails beyond its own tip and applies the diff, so *any* election winner converges to the acked frontier. Strictly stronger than the veto: instead of steering promotion to the caught-up node, it repairs whichever node promotes — the veto/challenger handshake then becomes an optimization rather than the safety mechanism, and the one case the veto can only warn about (a caught-up peer that dies *after* the primary, leaving its higher tip unreachable) shrinks to the window before its tail was pulled. Also heals the `disk+ram` case where a behind winner forces the caught-up replica's journal into a divergence archive. Cost is a new protocol role — a not-yet-promoted replica serving read-only journal tails on its already-bound replication port — with epoch fencing on that path (never serve a stale-epoch suffix) and mid-transfer failure handling; the existing `catch_up_from_journal` and streaming machinery is reusable, as is the shipped `PeerTips` tracking (it names the node to pull from). The `ram`-policy failover test (`crates/core/server-runtime/tests/replicated_failover.rs`) is the regression harness. |
| Determinism test in the counter example (snapshot vs replay) | Low | The README tells application authors they "inherit determinism as long as their logic stays pure", and gives them nothing to check that with. Three-way rather than two-way so a mismatch points at its cause — snapshot serialization or application logic. Ship it as the template a `melin-app` implementor copies for their own application; it is also the concrete example behind the README's testing claims. Independent of everything else. |

| Owned-buffer io_uring layer (kernel loans become moves) | Medium | The io_uring use-after-free class fixed across the replication sender, the replication receiver, and the client-facing reader (`crates/core/server-runtime/src/uring_teardown.rs` carries the shared teardown policy) had one root cause: buffers are *borrowed* to the kernel through `unsafe` SQE pushes, so the borrow checker's view ends where kernel ownership begins, and the discipline lives in SAFETY comments promising temporal invariants — four of which were wrong. No tool we run can see the class: ASan/TSan instrument CPU accesses (a kernel-side store into freed heap passed six ASan runs), and Miri cannot execute io_uring. Make the type system tell the truth instead, on the model tokio-uring/ringbahn established: a ring wrapper where submitting an op *moves* the buffer (or a move-only pool-lease token) into an in-flight ledger keyed by `user_data`, completions hand it back, and `Drop` runs the wake-then-bounded-drain-then-leak quiesce fed by the ledger — so freeing a kernel-held buffer, forgetting the quiesce, miscounting in-flight ops, or double-recycling a pool bid stops compiling rather than needing review. The `unsafe` concentrates into one audited module pinned by the existing socketpair tests; kernel-semantics assumptions (F_MORE terminality, shutdown-completes-RECV) stay test-verified. Migrate one transport at a time — sender first (smallest surface, freshest tests), then receiver (multishot + provided pool leases), then the reader (per-connection arms over the shared pool). Ledger is a fixed slab indexed by the `user_data` already assigned, moves are pointer copies — expected hot-path delta is noise, but benchmark before/after. Include the two detection layers that catch the class independent of the abstraction: a teardown-churn soak (connect/traffic/kill cycles across every ring-owning thread) and a test-profile quarantine allocator (delayed free + canary check) that turns a late kernel write into a deterministic failure; and fold the temporal-SAFETY grep (`outlives`/`until the CQE`/`stays alive` inside `unsafe` justifications) into the lockstep-confession audit below. Safety-slice prerequisite of the deferred "Unified transport abstraction over io_uring and DPDK" item, not a competitor to it. |
| Migrate the control plane to openraft 0.10 (once stable) | Medium | The 0.9 line draws each node's election timeout **once** at startup and campaigns on a fixed tick grid, which forced three in-tree compensations, each labeled as such at its definition: the deterministic per-node heartbeat offset in `melin-raft`'s driver (aligned-grid split votes), the election stand-down in `raft_promotion.rs` (a tip-behind replica re-winning doomed leaderships indefinitely, because the depose/re-elect race between fixed timeout draws has a fixed winner — observed livelocking failover past a 60 s deadline in ~5% of runs before the fix), and the challenger nudge's hold-down. | Document the in-flight order contract on pipeline halt | Low | The persist-before-ack gate (`crates/core/transport-core/src/pipeline.rs:746-750`) guarantees no client is acked for an event that lacks the copies the active ack policy demands (one or two fsynced copies, and/or a second in-memory copy). | Rebase fastcp on upstream smoltcp and prune the fork | Medium | `crates/core/dpdk/Cargo.toml:31` tracks our smoltcp fork on a feature branch (`melin-engine/fastcp`, branch `feat/zc-rx-window-and-index-eviction`), pinned in `Cargo.lock` several commits behind that branch's own head — the fix that stops the cached hardware address outliving its neighbor entry is on the branch but not in our lock. | Split replication off the DPDK client poll thread | Medium | On the DPDK path the replication driver runs **inline on the client poll loop**: `DpdkReplicationDriver::tick` is invoked from the same `dpdk_transport.rs` iteration that drains client responses to the wire and pulls client order packets off the NIC (`transport.poll()`), and the replication listener deliberately shares the trading queue (`server.rs`: the poll thread "accepts both trading and replication connections off the same queue"). This couples replication and the client hot path in **both directions**. **(a) Clients starve replication:** under heavy client load the replication sender doesn't get enough cycles to drain the ring, it fills, and a healthy replica is evicted. **(b) Replication stalls clients:** a replica handshake runs journal catch-up / snapshot transfer, and the catch-up→live handoff back-fill (`bridge_catchup_to_live`, bounded by `HANDOFF_BRIDGE_TIMEOUT`), inline on this poll thread — so for that duration the thread stops ingesting orders and sending acks for the clients on its queue. The matching/journal/response stages run on their own cores and keep processing already-ingested work; it is the NIC-facing RX/TX on the shared poll thread that pauses. Bounded today — the handoff spin is capped at 30 ms (typically microseconds on PLP+xfs), catch-up is the larger but pre-existing stall, and the kernel-TCP path is unaffected (each replica gets its own handler thread) — so **not urgent**. Fix: give replication its own core — a separate smoltcp socket set on a dedicated DPDK queue, or a shared-nothing handoff from the client poll thread — preserving the single-writer invariant on the replication ring (consumer side only). Promote when DPDK dual-replica reconnect latency becomes a diligence concern. ## DPDK Transport Optimization

| # | Optimization | Est. impact | Complexity | Description |
|---|-------------|------------|------------|-------------|
| 1 | Bypass smoltcp on hot path | Significant latency | Very high | For connected+authenticated clients, parse TCP directly from raw Ethernet frames. Eliminates smoltcp's per-packet overhead (neighbor lookup, socket dispatch, congestion window, timer checks). Custom minimal TCP for steady-state data path only. |
| 2 | Unified transport abstraction over io_uring and DPDK | Moderate maintainability, moderate latency | High | The TCP (io_uring) and DPDK code paths have independent replication senders, response writers, and connection handlers with duplicated logic that drifts (e.g. the journal-recreate-on-reconnect bug was fixed in TCP but not DPDK). Investigate a transport trait that captures the common interface (accept, connect, send, recv, poll) so the replication protocol, response stage, and connection state machine can be written once. The challenge is that io_uring is completion-based (submit SQE, reap CQE) while DPDK/smoltcp is poll-based (call poll, check buffers) — the abstraction must not penalize either model. |

## Deferred

Features with limited near-term value. Will revisit when the core product is mature or a specific buyer requires them.

| Feature | Why deferred |
|---------|-------------|
| SPDK journal | Userspace NVMe driver for journal writes. Bypasses kernel block layer entirely. TCP pipelining already hides fsync latency (fsync and no-persist throughput converged at ~8M/s), so the kernel block layer is no longer a bottleneck. High complexity, minimal expected gain. |
| io_uring journal writes | Shipped and then retired with the O_DIRECT sector writer: the journal stage used to submit `WRITE+RWF_DSYNC` async via io_uring, reaping CQEs non-blocking while encoding the next batch, with `IORING_OP_WRITE_FIXED` against registered batch buffers. The buffered writer is the only writer now, and its write path is being split across a dedicated disk thread instead. Revisit an io_uring backend only behind that thread's seam, and only if a trace shows the synchronous `pwrite`/`fdatasync` pair is the binding cost — note io-wq workers are anonymous, which breaks the thread-targeted off-CPU tracing every journal diagnosis here has depended on. |
| Vectored journal writes | Encode each event into its own stack buffer, pass as iovec array to `pwritev2`. Eliminates memcpy-per-event into the batch buffer. Small gain (~1-2µs/batch). |
| Verbatim byte-path journaling | Write the primary's encoded journal bytes directly on both primary and replica, skipping the decode/re-encode step on the replica side and an encode-from-struct pass on the primary. Saves CPU and reduces journal-stage work on the replay-critical path. Attempted once as a replica-only optimization (branch `replica-verbatim-journal`) but created an asymmetry that diverged fsync batching behavior between primary and replica — reverted in favor of a symmetric decode/re-encode on both sides. Revisit only with a plan to apply it on both sides simultaneously, preserving per-fsync size bounds. |
| io_uring RECVSEND_FIXED_BUF | `IORING_RECVSEND_FIXED_BUF` for registered buffer recv/send. Returned EINVAL on kernel 6.8; should work on 6.10+. Also test `IORING_RECVSEND_BUNDLE` for batched recv. Est. 15-25% throughput. |
| Dual-NVMe journal hedging | Two journal threads on separate NVMe drives, response stage gates on the fastest. Cuts tail latency from P(slow) to P(slow)². Free durability redundancy. Low complexity but requires a second NVMe slot. Revisit when journal fsync is the dominant tail contributor. |
| AF_XDP transport | DaMoN '25 found AF_XDP disappoints vs DPDK for small-message request-response workloads. DPDK transport already in progress. Revisit if DPDK proves insufficient. |
| Chain replication | Chain replication (primary → replica A → replica B) reduces primary fan-out. Dual parallel replication (up to 2 replicas) is implemented; chain topology is deferred. |
| TLS | Most exchange deployments use VLAN instead. Only needed for compliance-driven buyers. |
| Hybrid UDP multicast + TCP recovery for event channel | Current event channel is pure TCP. Multicast would reduce latency for co-located subscribers but adds complexity (gap detection, retransmit). Defer until a buyer needs sub-microsecond market data. |
